|------|------|
| 버전 | 2.2 (MVP + 병행 개발 절 추가) |

## 1. 문제 인식과 결론

**초기 4주 풀 플랫폼 계획**은 솔로·병행 일정 기준으로 과도했다.

**결론:** MVP로 슬라이스하고, 검색·리뷰·풀 관리자 UI 등은 **Phase 2(취업 후·여유 시)** 로 연기한다. 완벽한 UI보다 **작동·검증 가능한 스토리**를 우선한다.

---

## 2. MVP에서 증명할 것 / 하지 않을 것

### 증명 (4주 안)

- UGC **동작** (비주얼 에디터 수준 아님)
- 멀티 유저·세션 **격리**
- **BYOK** + 무료 티어 **쿼터**
- **Feature Flags**로 비용·가입 제어
- **실제 배포**(AWS 등)와 HTTPS
- 확장 시 **무엇을 키워야 하는지**(설정 + 인프라) 설명 가능

### 하지 않음 (MVP)

- SNS급 UI/UX
- 공개 탐색·검색·리뷰 시스템
- “코드 변경 없이 무한 확장” 같은 **과장** (아래 면접 스크립트 참고)

## 3. MVP vs Phase 2 (기능)

| 기능 | MVP | Phase 2 |
|------|-----|---------|
| 회원가입/로그인 | JWT | OAuth 등 |
| 초대 | 필수 코드 | 자동화·초대 링크 |
| BYOK | 필수 | 유지 |
| 월드/캐릭터 | **JSON 폼** + 템플릿 | 비주얼 빌더 |
| 프롬프트 | 템플릿 자동 생성 | AI 보조 등 |
| 공유 | **링크** (`/play/{world_id}`) | SNS 등 |
| 플레이 | HTTP POST 중심 채팅 | WS/SSE·고도화 |
| 탐색/검색 | 없음 | 목록·필터·추천 |
| 리뷰/평가 | 없음 | 선택 |
| 통계 | 최소 | 고급 분석 |
| 관리자 | 최소(초대·플래그) | 풀 대시보드 |

## 4. 정책 숫자 통일 (문서·README 공통)

혼동을 없애기 위해 **역할을 분리**한다.

| 개념 | 값 | 설명 |
|------|-----|------|
| **정책 상한** `MAX_TOTAL_USERS` | 100 (예시) | 가입 가능한 계정 수 **상한**. Feature Flag·DB로 제어 |
| **1차 베타 코호트** | ~10명 | 실제 초대할 사람 수. 모니터링·피드백용 |
| 무료 티어 일일 턴 | 20 | 플랫폼 키 사용 시 |
| 월드/인 (MVP) | 3 | Feature Flag와 일치 |
| 플랫폼 월 비용 **목표 상한** | ~$700 | 아래 비용 절 참고 |

README·발표 자료에는 **“비공개 베타, 초대 필요, 정책상 한도 N명”**처럼 쓰고, **실제 초대는 10명 근처**라고 구분해 적는 것을 권장한다.

---

## 5. 비용 (예산 vs 실측)

- **예산(보수적 가정):** 예) `$0.011/턴` × (100명 × 20턴 × 30일) ≈ **$660/월** — 플랫폼 키(무료 티어만) 기준 상한 추정.
- **실측:** 기존 엔진의 **`UsageTracker`** 및 Anthropic `usage`(input/output/cache)로 턴마다 합산. 캐시·2-pass·출력 길이에 따라 변동.
- **BYOK:** 해당 턴 비용은 **사용자 계정**에 청구. 플랫폼 비용 집계에서 **제외**.
- **알림:** 일일 플랫폼 비용 임계(예: $50) 초과 시 알림 + `EMERGENCY_SHUTDOWN` 등 문서화된 경로.

인프라(RDS·EC2)는 **별도**로 잡는다(베타 월 수십 달러 전후 가정 등).

---

## 6. 보안·개인정보 (MVP)

- 사용자 API 키: **암호화 저장(Fernet 등)**, 마스터 키는 시크릿 스토어. **운영자는 기술적으로 복호화 가능**함을 처리방침에 명시.
- 베타: 신뢰 가능한 소수만 초대해도, **최소한의 개인정보·키 취급 문구**는 두는 것을 권장.
- `.env`를 EC2에 `echo`로만 두지 말고 **SSM Parameter Store / Secrets Manager** 등을 목표로 명시.

---

## 7. 배포·Docker 원칙 (요약)

- **의존성:** 저장소는 **Poetry** 기준 — 이미지 빌드 시 `poetry install` 패턴.
- **마이그레이션:** 앱 워커 기동과 분리(전용 one-shot job / init 컨테이너). 여러 worker가 동시에 `alembic upgrade` 하지 않도록.
- **uvicorn workers:** 베타는 **2**부터(메모리). t3.small 등에서 4 worker는 과할 수 있음.
- **Feature Flags:** 멀티 워커면 클래스 변수만으로는 불일치 가능 — **DB(또는 Redis) 읽기** + 필요 시 짧은 TTL 캐시.

---

## 8. 타임존

- DB: **UTC (`TIMESTAMPTZ`)**, 일일 쿼터 리셋 기준은 **문서에 한 가지로 고정**(예: UTC 자정).
- UI: 사용자 로컬 표시만 달리 할 수 있음.

---

## 9. 데이터·스키마 주의 (MVP)

- `users.created_worlds`에 **CHECK로 3 고정**하지 말고, **`worlds` COUNT** 또는 트리거로 정책 일치.
- `invite_codes.created_by`: 관리자 삭제 시 초대 행이 사라지지 않게 **`ON DELETE SET NULL`** 등 검토.
- **단일 진실의 원천:** 플레이 상태·장기 기억을 DB에 둘 때, 파일 `memories.json`과 **이중 갱신**되지 않게 경계를 한 번에 정한다.

## 11. 병행 개발 (백엔드 + 프론트 동시)

API만 먼저 주 단위로 쌓다가 UI를 나중에 붙이면, 나중에 **응답 스키마·에러 형식**을 다시 깨는 경우가 많다. MVP는 **수직 슬라이스**로 진행한다: **작은 API 조각 → 같은 날/다음 날 UI 연동 → 화면에서 확인**.

### 11.1 주차별 “끝에 보이는 것”

| 주차 | 백엔드(요약) | 프론트(요약) | 주말 끝 상태 |
|------|--------------|--------------|--------------|
| **Week 1** | DB, signup/login, JWT, 초대, BYOK·Tier | Vite·Router, 로그인/회원가입/설정 UI | **로그인·가입·키 등록이 눈에 보임** |
| **Week 2** | 월드 CRUD, 검증, 프롬프트 템플릿 | 목록·생성 폼·프리뷰 | **월드 만들기·목록이 보임** |
| **Week 3** | GameEngine·세션·공유 링크 | 채팅 화면·관계 게이지 | **플레이 한 사이클이 보임** |
| **Week 4** | 플래그·레이트리밋·Docker·배포 | 반응형·에러 UX·다듬기 | **배포 URL에서 데모 가능** |

### 11.2 시간 배분 (가이드)

| 주차 | 백엔드 | 프론트 | 비고 |
|------|--------|--------|------|
| Week 1 | ~60% | ~40% | DB·인프라 셋업 비중 |
| Week 2 | ~50% | ~50% | CRUD·폼 균형 |
| Week 3 | **~50–60%** (초반 더 백엔드) | ~40–50% | 엔진·세션 API가 최대 리스크 |
| Week 4 | ~30% | ~70% | 폴리시·반응형·마감 |

Week 3은 표상 40% 백엔드로만 두기 어렵다. **월~화는 엔진/세션 API에 백엔드 비중을 더** 두고, 채팅 UI는 병행하되 “빈 껍데기 → 연동” 순으로 가도 된다.

### 11.3 플레이 전송 방식 (MVP 고정)

- **기본:** 턴당 **HTTP POST** + 로딩 표시. §3·§13과 동일.
- **WebSocket / SSE / 폴링:** 여유·필요 시만. MVP 완료 정의에서 **필수 아님**.

### 11.4 Day 0·병행 시 공통 준비

- **CORS:** 프론트에서 API 호출 시작 전에 FastAPI `CORSMiddleware`와 허용 오리진 확정.
- **베이스 URL:** Vite는 `VITE_API_URL`(또는 dev proxy)을 **첫 연동 전**에 고정해 두기.
- **초대 코드:** 가입이 초대 필수면 `POST /api/auth/signup` **첫 스펙부터** `invite_code` 필드를 넣고, UI도 같은 주에 맞춘다 (나중에 필드 추가보다 안전).

### 11.5 Week 1이 빡빡할 때 (필수 vs 완화)

**Week 1 필수 (데모 최소):** DB + signup/login + JWT + **초대 검증 포함 가입** + 프론트 로그인/가입·토큰 보관.

**Week 1 후반으로 미뤄도 되는 것:** BYOK UI·설정 페이지 일부, 스타일 다듬기 → **Week 2 초**로 넘겨도 된다. 문서 완료 정의는 “Week 1~2 합쳐서 인증+BYOK 완료”로 조정 가능.

### 11.6 팁: API 직후 UI, Mock

- **나쁜 예:** 한 주 전체를 API만 작성 → 다음 주 UI → 이때 스키마 불일치 발견.
- **좋은 예:** 오전 signup API → 오후 signup 폼 + 연동; 다음 날 login 동일.
- **Mock:** 백엔드가 늦으면 `mockWorlds` 등으로 목록·카드 UI를 먼저 그린 뒤 `fetch`만 교체.

## 12. MVP 성공 기준 (완화된 베타)

**기술**

- 초대·로그인·BYOK·월드 CRUD·공유 링크·플레이·세션 격리가 **끝까지 한 번** 동작
- 플랫폼 비용 **추적** 가능; 상한 알림 경로 정의
- 테스트 커버리지 목표 예: **60%+** (80%는 비필수)

**베타 운영**

- 1차 초대 **~10명**, DAU 등은 과도한 KPI 대신 **피드백·에러 로그** 우선
- API P99 등은 **10s 이하** 등 완화 목표 가능

## 13. 면접용 한 줄 (과장 방지)

> “가입 한도·쿼터·초대는 **설정과 DB**로 바꿀 수 있게 열어 두었고, 트래픽이 커지면 **EC2/RDS 스펙·연결 풀·관측**은 별도로 키워야 합니다. 비용은 **BYOK**로 플랫폼 부담을 줄이고, 무료 턴은 **상한**을 둡니다.”
